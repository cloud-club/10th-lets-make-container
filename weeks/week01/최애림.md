# 1주차 심화 질문 정리

## 실습에서 생긴 의문: 같은 프로세스인데 왜 PID가 다를까

컨테이너에서 `sleep 100`을 실행했더니
- 컨테이너 안에서는 PID **15**
- 호스트에서는 PID **39142**

**하나의 프로세스가 번호를 두 개 갖고 있는 상태**다.

`docker run`이 컨테이너를 띄울 때 새로운 PID namespace를 만들고, 그 안에서는 번호를 1번부터 다시 매기기 때문이다.

| 어디서 보느냐 | PID | PPID |
|---|---|---|
| 컨테이너 안 | 15 | 1 (sh) |
| 호스트 | 39142 | 39000 (sh) |

확인해보기:

```bash
sudo cat /proc/39142/status | grep NSpid
# NSpid:  39142  15
```

왼쪽이 호스트 번호, 오른쪽이 컨테이너 번호다. 호스트에서 `kill 39142`를 하면 컨테이너 안의 `sleep`이 종료된다. 같은 프로세스이기 때문이다.

---

## 1. `/proc/<PID>`는 실제 저장된 파일일까

### 답: 아니다

디스크에 저장된 파일이 아니다. **읽는 순간 커널이 만들어서 보여주는** 내용이다.

확인 방법:

```bash
# 1) 마운트 정보에 디스크(블록 디바이스)가 없다
mount | grep proc
# proc on /proc type proc (rw,nosuid,nodev,noexec)

# 2) 파일 크기가 0이다 (내용이 저장돼 있지 않으니까)
ls -l /proc/1/status

# 3) 그런데 cat 하면 내용이 나온다
cat /proc/1/status
```

크기가 0인데 내용이 나온다. `cat`을 실행한 시점에 커널이 메모리에 있는 프로세스 정보를 글자로 바꿔서 전달하기 때문이다.

### 왜 이렇게 만들었나

프로그램이 **특별한 명령 없이 파일 읽듯이** 커널 정보를 가져갈 수 있게 하려는 것이다.

`ps`, `top`, `pstree`는 모두 `/proc` 폴더를 읽어서 목록을 만든다. 이 점이 3번 답으로 이어진다.

### `/proc/<PID>/` 안에 있는 것들

| 종류 | 예시 | 성격 |
|---|---|---|
| 읽을 때 생성되는 글자 | `status`, `stat`, `cmdline` | 크기 0 |
| 심볼릭 링크 | `exe`, `cwd`, `fd/` | 실제 대상을 가리킴 |
| namespace 정보 | `ns/` | 격리 상태 확인용 |

## 2. 자식이 죽은 뒤 부모가 종료 상태를 회수해야 하는 이유

### 좀비가 뭔가

자식 프로세스가 죽어도 커널은 그 흔적을 바로 지우지 못한다. **부모가 "얘 몇 번으로 끝났어?"를 아직 안 물어봤을 수 있기 때문이다.**

그래서 메모리 같은 건 다 반납하고 **번호(PID)랑 종료 코드만 남긴 껍데기**로 남겨둔다. 이게 좀비(zombie) 상태다.

일은 끝났는데 퇴사 처리만 남은 상태라고 보면 된다.

### 안 치우면 뭐가 문제인가

- **번호가 바닥난다.** PID는 무한하지 않다 (`/proc/sys/kernel/pid_max`). 좀비가 계속 쌓이면 결국 새 프로세스를 못 만든다.
- **`kill -9`로도 제거되지 않는다.** 이미 종료된 상태이기 때문이다. 없애려면 **부모를 종료해야** 한다.

부모가 먼저 종료되면 남은 자식은 PID 1번에게 넘어가고(재부모화), 1번이 대신 회수한다. init의 역할이 이것이다.

### 어떤 system call을 쓰나

`wait` 계열이다.

```c
wait(&status);                        // 자식 아무나 하나 기다림
waitpid(pid, &status, options);       // 특정 자식 지정 가능 (제일 많이 씀)
waitid(...);                          // 더 자세한 정보
wait4(...);                           // CPU/메모리 사용량까지
```

실무에서 자주 보는 패턴:

```c
// 블로킹 없이 밀린 좀비만 회수
while (waitpid(-1, NULL, WNOHANG) > 0)
    ;
```

`WNOHANG`은 회수할 자식이 없으면 즉시 리턴하라는 옵션이라 프로그램이 멈추지 않는다.

받아온 `status`는 이렇게 해석한다.

| 매크로 | 의미 |
|---|---|
| `WIFEXITED` | 정상 종료했나 |
| `WEXITSTATUS` | 종료 코드는 몇인가 |
| `WIFSIGNALED` | 시그널 맞고 죽었나 |
| `WTERMSIG` | 무슨 시그널인가 |

### 컨테이너랑 무슨 상관인가

이번 실습에서 컨테이너의 1번은 `sh`였다.

**일반 셸이나 애플리케이션에는 좀비를 회수하는 기능이 없다.** 그래서 컨테이너 PID 1에 아무 프로세스나 두면 좀비가 계속 쌓인다.

하나 더. **PID 1은 시그널 기본 동작이 적용되지 않는다.** 보통 프로세스는 `SIGTERM`을 받으면 종료되지만, PID 1은 처리 코드를 직접 넣지 않으면 무시한다. 그래서 `docker stop`이 10초 기다렸다가 `SIGKILL`로 강제 종료하게 된다. 컨테이너 종료가 유독 느린 경우의 흔한 원인이다.

### 해결책: `--init`

PID 1 자리에 그 일을 할 줄 아는 프로그램을 앉히면 된다. **tini**가 그 역할이고, 하는 일은 두 가지다.

- 넘어온 좀비를 `wait()`로 회수
- 받은 시그널을 자식에게 전달

`--init` 옵션을 주면 도커가 tini를 1번 자리에 넣고, 원래 실행하려던 명령은 그 아래 자식으로 내려간다.

```bash
docker run --init -it --rm busybox sh
```

```
# 옵션 없음              # --init 사용
sh(1)                    tini(1)
 └─ myapp(7)              └─ sh(7)
                              └─ myapp(9)
```

컨테이너 안에서 `ps -ef`를 보면 PID 1이 tini로 나온다. 컨테이너 안에서 자식 프로세스를 여러 개 띄울 때 필요하고, 애플리케이션 하나만 도는 단순한 컨테이너면 없어도 된다.

## 3. 호스트에서는 컨테이너 프로세스가 보이는데 왜 반대는 안 보일까

### 한 줄 요약

**부모는 자식을 보지만, 자식은 부모를 못 본다.**

### 비유로 먼저

호스트를 회사 전체, 컨테이너를 그 안에 새로 만든 팀이라고 해보자.

- 회사 사번은 39142번까지 나갔다.
- 새 팀은 **팀 내부 번호를 1번부터 다시 매긴다.**
- 그래서 같은 사람이 회사 사번 39142, 팀 번호 15를 동시에 갖는다.

**팀 명단에는 팀원만 적혀 있다.** 다른 부서 사람은 이 명단에 번호가 없다. 그래서 컨테이너 쪽에서는 호스트 프로세스를 지칭할 방법 자체가 없다.

회사 인사팀 명단에는 전원이 있으므로 팀원도 보인다.

### 정확히 말하면

PID namespace는 트리 구조다.

```
호스트 namespace
  └─ 컨테이너 namespace
```

프로세스는 자기 namespace뿐 아니라 **위쪽 namespace 전부에서 각각 번호를 받는다.** 그래서 `sleep`이 39142와 15를 동시에 갖는다.

호스트의 `dockerd`(701)는 컨테이너 namespace에서 번호를 받은 적이 없다. 컨테이너 안에서 이 프로세스를 가리킬 번호가 존재하지 않는다.

호스트에서 전부 보이는 이유는 **컨테이너가 호스트 커널이 직접 실행하는 프로세스**이기 때문이다.

### 그런데 PID namespace만으로는 부족하다

1번에서 봤듯이 `ps`는 **`/proc` 폴더를 읽어서 목록을 만든다.**

컨테이너가 호스트의 `/proc`을 그대로 보고 있으면, 번호를 새로 매겨도 `ps`에는 호스트 프로세스가 그대로 나온다.

그래서 컨테이너는 **자기 전용 `/proc`을 따로 마운트**한다. PID namespace(번호 격리) + mount namespace(`/proc` 격리) 두 개가 같이 있어야 진짜로 안 보인다.

직접 확인해보면 차이가 보인다.

```bash
# /proc 격리 없음 -> 호스트 프로세스가 그대로 보임
sudo unshare --pid --fork ps -ef

# /proc까지 격리 -> 자기 프로세스만 보임
sudo unshare --pid --fork --mount-proc ps -ef
```

### 정리

| | 호스트 | 컨테이너 |
|---|---|---|
| 번호 기준 | 전체 | 자기 namespace |
| `/proc`에 있는 것 | 전부 | 자기 것만 |
| 상대가 보이나 | 보인다 | 안 보인다 |

### 예외

```bash
docker run --pid=host ...
```

namespace를 나누지 않으므로 컨테이너에서도 호스트 PID가 그대로 보인다. 모니터링이나 디버깅용 컨테이너가 이 방식을 쓴다. 격리를 포기하는 설정이므로 일반 서비스에는 쓰지 않는다.

쿠버네티스에서 Pod 안 컨테이너끼리 프로세스를 공유하는 `shareProcessNamespace: true`도 같은 원리다.

## 세 질문이 이어지는 지점

1번에서 확인한 "`/proc`은 커널 상태를 보여주는 창구"라는 점이, 3번의 "`/proc`이 다르면 보이는 프로세스도 다르다"로 이어진다.

2번의 "PID 1은 좀비를 회수해야 한다"는 컨테이너 PID 1 선택이 중요한 이유가 된다.

세 질문 모두 이번 주 주제인 **"컨테이너는 격리 옵션이 붙은 리눅스 프로세스"**를 다른 각도에서 확인한다.
