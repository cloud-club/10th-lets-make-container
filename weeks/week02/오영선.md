# 1주차 질문
/proc/<PID>는 실제 저장된 파일일까?
-> 아님! 실제로는 하나의 프로세스(프로그램)인데 파일처럼 보이게 만든것.(인터페이스화)

자식 프로세스가 종료된 뒤 부모가 종료 상태를 회수해야 하는 이유는 무엇이며, 이때 어떤 system call을 사용할까?
-> 회수안하면 자식은 죽었지만 정보만 남아있는 좀비(zombie) 상태가 됨. 커널 깔끔하게 정리하게
-> wait() / waitpid()

호스트에서는 컨테이너 프로세스가 보이는데, 컨테이너에서는 대부분의 호스트 프로세스가 보이지 않는 이유는 무엇일까?
-> PID namespace 기능으로 보이는걸 격리했기때문

# 2주차 질문
1. BusyBox 이미지 : 컨테이너를 만들 때 쓰는 기본 재료
   docker create: 기본재료를 이용해서 컨테이너를 만들기
   tmproot: 컨테이너 안에 있던 파일을 밖으로 꺼낸 폴더
   즉, BusyBox → 컨테이너 → 파일을 꺼내놓은 tmproot 순서이다.

2.ps는 /proc를 보고 프로세스 목록을 확인함.
호스트의 /proc를 컨테이너에 연결하면 호스트의 프로세스 목록을 볼수있음.
마운트 전에도 프로세스 격리X, 그냥 컨테이너용 /proc를 보고 있어서 호스트 프로세스가 안보였던것.
(보는 장치가 같아도 보는 화면이 다른 것)

3.chroot cd ..로 위로 올라가는 건 막을수있음
하지만 이미 다른 곳으로 연결된 권한, 열린 파일이 있으면 그걸로 밖의 자원에 접근가능.
그래서 chroot만으로는 완전한 격리가 불가능하고, 파일 경로만 제한하는 용임.
